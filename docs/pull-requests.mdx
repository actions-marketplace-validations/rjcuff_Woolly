---
title: Pull request checks
description: A GitHub Action that comments on a pull request when it makes a line in CLAUDE.md, AGENTS.md or a project fact stale, with the commit that did it, so someone reviews it before it merges.
---

When a pull request changes code that a line in CLAUDE.md, AGENTS.md, Cursor rules or `.woolly/woolly.md` names, Woolly comments on it.

> **Woolly** checked 48 lines in CLAUDE.md and AGENTS.md. **1 line in agent files went stale.**
>
> Agents read these as true, but the code no longer has what they name. Each one is a line for a person to review, with the commit that changed the code. Woolly doesn't check whether the code itself is right.
>
> | Line | Says | What changed |
> | --- | --- | --- |
> | `CLAUDE.md:12` | `- Handlers call requireUser first` | requireUser was renamed to requireSession in src/auth.ts in 229f599 (2026-11-20) |

Each finding is evidence, not a verdict. It gives the line, what it names, and the commit where that name, file, script or make target went away. A person decides whether the line is wrong. Woolly matches names against git history with no model, so it can miss a line whose meaning went stale while every name in it still exists.

Nobody on the team needs Woolly installed for this.

## Set it up

Add `.github/workflows/woolly.yml` to your repo.

```yaml
name: Woolly
on: pull_request

permissions:
  contents: read
  pull-requests: write

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: rjcuff/woolly@action-v1
        with:
          version: "0.18.0"
```

That's it. It checks the repo's agent files, like CLAUDE.md, AGENTS.md and Cursor rules, with no setup. See [Check your agent files](/docs/memory-files). With [project memory](/docs/project-memory) committed by `woolly init`, it checks those facts too. See [Stale facts](/docs/stale-facts). `fetch-depth: 0` lets Woolly read the history it needs to tell what changed.

### Pin what runs

`version` pins the Woolly release the Action downloads, so a new release can't change your checks until you choose it. `action-v1` pins the Action's own steps to its major version. To pin those exactly too, use a full commit SHA instead, like `rjcuff/woolly@<40-character SHA>`, and let Dependabot or Renovate propose updates.

### Permissions

| Permission | Why |
| --- | --- |
| `contents: read` | To check out the repo and read its history |
| `pull-requests: write` | To post and update Woolly's one comment. Leave it out, and set `comment: "false"`, to only write the job summary |

The Action needs nothing else, and it never pushes commits.

## How it works

1. It downloads Woolly from the [GitHub release](https://github.com/rjcuff/woolly/releases) you pinned and checks it against the checksum published with that release. If the checksum doesn't match, the job stops.
2. It reads the facts from `.woolly/woolly.md` into a Woolly of its own for the job.
3. It runs `woolly check --markdown --base <the pull request's base commit>`. Facts were true on the branch you're merging into, so that's what the change is compared against.
4. It checks every line in the repo's agent files and reports the ones this change made stale. Lines that were already out of date are listed separately, folded away.
5. It writes the report to the job summary. When something went stale, it comments on the pull request. If it commented before, it updates that comment instead of adding another.
6. It marks each stale line in the pull request's Files changed view, next to the line, when that file is part of the change. Lines this change made stale are warnings, and lines that were already stale are notices.

The comment quotes each stale line as code, so a line can't mention people, load images, add links or render HTML in the comment. A line that looks like it holds an API key, token or password is not quoted at all.

## Where your data goes

- The check runs on your GitHub runner, GitHub's or your own, against your checkout. It uses no model and sends nothing to Woolly. Only if your organization installs the optional [Woolly Team](/team) app does Team read the run's status file, which holds counts and file pointers.
- The runner downloads Woolly from GitHub releases. With the default comment setting it also calls the GitHub API to post the comment.
- The report, which quotes the stale lines, goes to the job log, the job summary and, when something went stale, a pull request comment. Anyone who can read the repo's Actions and pull requests can read those. In a public repo that's everyone.
- Personal memory, like Claude Code's auto memory and Codex memories, lives in the home folder of your own computer, not on GitHub's runners, so the Action doesn't see it. On a self-hosted runner, run the job as a user who has none.

## Options

| Input | Default | What it does |
| --- | --- | --- |
| `version` | `latest` | The Woolly release to run, like `0.18.0`. `latest` runs the newest one. `preinstalled` uses the `woolly` already on the PATH, for runners that install it themselves |
| `base` | the pull request's base commit | The commit or branch to compare against. On a push, it defaults to the commit before the push |
| `comment` | `true` | Comment on the pull request when something goes stale. `false` only writes the job summary |
| `fail-on-stale` | `false` | Fail the job when the change makes something stale |
| `annotations` | `true` | Mark each stale line in the pull request's changed files. `false` leaves them out. Needs Woolly 0.21.0 or later |
| `footer` | `true` | End the comment with one line that links to Woolly. `false` leaves it out |
| `token` | `github.token` | The token for commenting. It needs `pull-requests: write` |

## Outputs

| Output | What it is |
| --- | --- |
| `new-stale` | Facts and agent file lines this change made stale |
| `already-stale` | Ones that were already stale before this change, or waiting for review |
| `lines-checked` | Lines checked in the repo's committed agent files |
| `checked` | Project facts that point at code that were checked |
| `stale` | The same as `new-stale`, kept for workflows that use it |
| `status-file` | The path of the `--status-json` file for this check, described below |

`new-stale`, `already-stale` and `lines-checked` need Woolly 0.18.0 or later. With an older `version`, they're 0 and the job warns.

## Pull requests from forks

Use `on: pull_request`. Don't use `pull_request_target` for this check: it runs with a token that can write to your repo while checking out code from someone else's fork.

GitHub gives pull requests from forks a token that can't comment. The check still runs and the report is still in the job summary.

## Status for other tools

`woolly check --status-json` prints the result as counts and pointers: the commit checked, how many facts and lines, how many went stale in this change and how many already were, and for each stale line its file, line number, kind and the commit that changed the code. It has no text from your agent files, facts or code, and leaves out memory that isn't a file committed to the repo. `--status-file <path>` writes the same thing next to `--markdown`.

```json
{
  "schema": "woolly.check.status/v1",
  "woolly_version": "0.18.0",
  "head": "48382c1db93c",
  "base": "02e5cfb5528a",
  "checked": { "facts": 0, "files": 1, "lines": 3 },
  "stale": { "new": 2, "before": 1 },
  "findings": [
    { "type": "agent_file_line", "state": "new", "file": "CLAUDE.md", "line": 2, "kind": "name", "commit": "48382c1" }
  ]
}
```

The Action writes this file for every check. To keep it with the workflow run, give the Woolly step an `id` and upload the file:

```yaml
      - uses: rjcuff/woolly@action-v1
        id: woolly
        with:
          version: "0.18.0"
      - uses: actions/upload-artifact@v4
        with:
          name: woolly-status
          path: ${{ steps.woolly.outputs.status-file }}
          retention-days: 14
```

## GitLab and Bitbucket

The GitHub Action is the easiest setup, but the check runs anywhere with git and a shell. These pipelines install Woolly, check the merge request against its base, and post the report as a comment when something went stale. Unlike the Action, they add a new comment each time instead of updating one.

### GitLab

Add a [project access token](https://docs.gitlab.com/user/project/settings/project_access_tokens/) with the `api` scope and the Reporter role as a masked CI/CD variable named `WOOLLY_GITLAB_TOKEN`. Without it, the report only goes to the job log.

```yaml title=".gitlab-ci.yml"
woolly:
  image: debian:bookworm-slim
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  variables:
    GIT_DEPTH: "0" # the check needs the base commit
    WOOLLY_HOME: "$CI_PROJECT_DIR/.woolly-home"
    WOOLLY_NO_EMBED: "1"
  script:
    - apt-get update -qq && apt-get install -y -qq git curl ca-certificates jq > /dev/null
    - curl -fsSL https://usewoolly.com/install.sh | WOOLLY_INSTALL_DIR="$CI_PROJECT_DIR/.woolly-bin" sh
    - export PATH="$CI_PROJECT_DIR/.woolly-bin:$PATH"
    - set +e; woolly check --markdown --no-backfill --base "$CI_MERGE_REQUEST_DIFF_BASE_SHA" > report.md; code=$?; set -e
    - cat report.md
    - |
      if [ "$code" = 1 ] && [ -n "$WOOLLY_GITLAB_TOKEN" ]; then
        jq -n --rawfile body report.md '{body: $body}' | curl -fsS -X POST \
          -H "PRIVATE-TOKEN: $WOOLLY_GITLAB_TOKEN" -H "Content-Type: application/json" --data @- \
          "$CI_API_V4_URL/projects/$CI_PROJECT_ID/merge_requests/$CI_MERGE_REQUEST_IID/notes" > /dev/null
      fi
    - '[ "$code" -le 1 ]' # stale lines don't fail the job; use '[ "$code" = 0 ]' to fail it
```

### Bitbucket

Add a [repository access token](https://support.atlassian.com/bitbucket-cloud/docs/repository-access-tokens/) with the **Pull requests: Write** scope as a secured repository variable named `WOOLLY_BITBUCKET_TOKEN`.

```yaml title="bitbucket-pipelines.yml"
pipelines:
  pull-requests:
    "**":
      - step:
          name: Woolly check
          image: debian:bookworm-slim
          clone:
            depth: full # the check needs the base commit
          script:
            - apt-get update -qq && apt-get install -y -qq git curl ca-certificates jq > /dev/null
            - curl -fsSL https://usewoolly.com/install.sh | WOOLLY_INSTALL_DIR="$BITBUCKET_CLONE_DIR/.woolly-bin" sh
            - export PATH="$BITBUCKET_CLONE_DIR/.woolly-bin:$PATH" WOOLLY_HOME="$BITBUCKET_CLONE_DIR/.woolly-home" WOOLLY_NO_EMBED=1
            - git fetch origin "$BITBUCKET_PR_DESTINATION_BRANCH"
            - BASE=$(git merge-base HEAD "origin/$BITBUCKET_PR_DESTINATION_BRANCH")
            - set +e; woolly check --markdown --no-backfill --base "$BASE" > report.md; code=$?; set -e
            - cat report.md
            - >
              if [ "$code" = 1 ] && [ -n "$WOOLLY_BITBUCKET_TOKEN" ]; then
              jq -n --rawfile raw report.md '{content: {raw: $raw}}' | curl -fsS -X POST
              -H "Authorization: Bearer $WOOLLY_BITBUCKET_TOKEN" -H "Content-Type: application/json" --data @-
              "https://api.bitbucket.org/2.0/repositories/$BITBUCKET_REPO_FULL_NAME/pullrequests/$BITBUCKET_PR_ID/comments" > /dev/null;
              fi
            - '[ "$code" -le 1 ]'
```

Both pipelines run on your own runners against your checkout, like the Action, and send nothing to Woolly. Woolly Team's dashboard only reads GitHub for now.

## Run the same check yourself

```sh
woolly check --markdown --base origin/main
```
