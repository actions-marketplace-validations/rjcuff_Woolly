---
title: Memory API for agents
description: Give the agents you build a memory that learns, with mem0's API on your own machine.
---

Woolly's memory layer API lets the agents and apps you build remember their users. Send it a conversation and it pulls out the facts worth keeping, then decides for each one whether it's new, changes something it already knows, or says something is no longer true. Search it before your agent answers.

It uses mem0's routes and field names, so code written for mem0 needs little more than a new address. Everything runs on your machine with a local model in [Ollama](/docs/ollama).

```sh
woolly serve
TOKEN=$(cat ~/.woolly/token)
```

Every request needs the token, as `Authorization: Bearer $TOKEN` or mem0's `Authorization: Token $TOKEN`.

## Add a conversation

```sh
curl -X POST localhost:11435/v1/memories \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "messages": [
      {"role": "user", "content": "I just moved to Austin, and I stopped using Vim"},
      {"role": "assistant", "content": "Got it"}
    ],
    "user_id": "alice"
  }'
```

```json
{
  "results": [
    {"id": "20261116-...", "memory": "Lives in Austin", "event": "UPDATE", "previous_memory": "Lives in Denver"},
    {"id": "20261110-...", "memory": "Uses Vim", "event": "DELETE"}
  ]
}
```

For each fact, the local model sees the closest memories in the same scope and picks an event:

| Event | What happened |
|---|---|
| `ADD` | A new fact was saved. |
| `UPDATE` | The fact replaced an older one about the same thing. The old one is kept as history. |
| `DELETE` | An existing memory is no longer true. It's kept as history, marked with when it stopped. |
| `NONE` | Woolly already knew it. |
| `CONFLICT` | The fact disagrees with something the user said themselves, so it waits for them to review it. |

Your version always wins. The model can change what it inferred, but never what a person stated directly. That becomes a `CONFLICT` you resolve in the [review page](/docs/review).

Send `"infer": false` to save each user message as it is, without a model. Add `"metadata": {...}` to attach your own data to every memory saved.

## Scopes

`user_id`, `agent_id` and `run_id` keep memories apart, the same way mem0 uses them. A memory saved for `alice` is never shown to, or changed by, `bob`. Add `project` to keep a fact to one codebase. Leave them all out to use your own personal memory.

Memories saved with a `user_id`, `agent_id` or `run_id` belong to your app, not to you, so they never show up in your own AI apps. They aren't in the brief Claude Code gets at the start of a session, not in the MCP `recall`, `get_profile` or `list_memories` tools, and not in the notes the proxy adds. Add the same scope to `GET`, `PUT` or `DELETE /v1/memories/{id}` and `/history` and a memory outside it returns 404, so one of your users can't reach another's memories by ID.

## Search

```sh
curl -X POST localhost:11435/v1/search \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"query": "where does she live", "filters": {"user_id": "alice"}, "top_k": 5}'
```

Results are scored by meaning, keywords and how recent they are. `threshold` drops weak matches, and `show_expired` includes memories that are no longer true, for questions about the past. The scope fields also work at the top level, as older mem0 clients send them.

## Kinds of memory

Give a memory a type so your agent can ask for just what it needs:

- `preference`: how someone likes things, like "wants bullet-point summaries"
- `procedure`: how to do something, like "to reset a password, send the link from the admin page"
- `episode`: something that happened, like "the March 3 outage was a bad config push"

Project facts can also be a `decision`, `convention`, `gotcha`, `bug` or `hardware`.

Add `"memory_type": "procedure"` when you add messages, and `"type": ["procedure"]` in search `filters` to get only those. Each result has its `type`.

```sh
curl -X POST localhost:11435/v1/search \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"query": "reset a password", "filters": {"user_id": "alice", "type": ["procedure"]}}'
```

The type is in the memory's Markdown header, so you can change it by hand.

## Links

Tie two related memories together and searching for one brings the other along, at half its score:

```sh
curl -X POST "localhost:11435/v1/memories/$ID/links?user_id=alice" \
  -H "Authorization: Bearer $TOKEN" -d '{"to": "'$OTHER'"}'
```

Both memories must have the same `user_id`, `agent_id` and `run_id`. Links are a `links:` line in the Markdown header.

## Conflicts

When an AI's version of a fact disagrees with a more trusted one, it waits as a conflict. `GET /v1/conflicts?user_id=alice` lists them, each with the memory it disagrees with. `POST /v1/conflicts/{id}/resolve` keeps one. Your app can only keep a version at least as trusted as the ones it replaces; otherwise it gets 403, and the user settles it on the [review page](/docs/review).

## Feedback

Tell Woolly whether a memory helped, and it ranks helpful memories a little higher next time and unhelpful ones a little lower. Nothing is hidden or deleted because of feedback.

```sh
curl -X POST "localhost:11435/v1/memories/$ID/feedback?user_id=alice" \
  -H "Authorization: Bearer $TOKEN" -d '{"helpful": false}'
```

Woolly also counts each time a memory is recalled or put in a session brief. Counts and feedback live in `~/.woolly/usage.json` on this device. They are never synced or written into the Markdown files.

## Memories over time

Nothing is overwritten. When a fact changes, the old version stays on disk with `status: superseded` and an `invalid_at` time, and an expired fact gets `status: expired`. Ask for the whole story of a memory:

```sh
curl localhost:11435/v1/memories/ID/history -H "Authorization: Bearer $TOKEN"
```

```json
{
  "results": [
    {"memory_id": "...", "event": "ADD", "old_memory": null, "new_memory": "Lives in Denver"},
    {"memory_id": "...", "event": "UPDATE", "old_memory": "Lives in Denver", "new_memory": "Lives in Austin"}
  ]
}
```

## All routes

| Method | Path | Does |
|---|---|---|
| `POST` | `/v1/memories` | Add a conversation: `messages`, scope, `metadata`, `infer`, `memory_type` |
| `GET` | `/v1/memories` | List memories in a scope: `user_id`, `agent_id`, `run_id`, `project`, `top_k`, `show_expired` |
| `GET` | `/v1/memories/{id}` | One memory |
| `PUT` | `/v1/memories/{id}` | Change `text` or `metadata`, keeping the old version as history |
| `DELETE` | `/v1/memories/{id}` | Move a memory to the trash |
| `DELETE` | `/v1/memories` | Move every memory in a scope to the trash. Needs a `user_id`, `agent_id` or `run_id` |
| `GET` | `/v1/memories/{id}/history` | Every version, oldest first |
| `POST` | `/v1/memories/{id}/links` | `to`: another memory's ID. Recalling one brings the other along |
| `GET` | `/v1/conflicts` | Conflicts in a scope, each with what it disagrees with |
| `POST` | `/v1/conflicts/{id}/resolve` | Keep this version. 403 if it would replace something more trusted |
| `POST` | `/v1/memories/{id}/feedback` | `helpful`: true or false. Nudges ranking |
| `POST` | `/v1/search` | Search: `query`, `filters` (scope and `type`), `top_k`, `threshold`, `show_expired` |
| `POST` | `/v1/dream` | Tidy a scope and learn lessons: `dry_run`, `learn`. See [Dreaming](/docs/dreaming) |

Every memory is still a Markdown file in `~/.woolly/memories`, with its scope in the header, so you can read and fix what your agents learned.
